# DXP4800 Pro: Additional technical evidence

This reference records **additional**, dated troubleshooting evidence and unresolved discrepancies. It complements, but does not replace, the [Debian recovery guide](DEBIAN13_DXP4800PRO.md), [fan-control details](FAN_CONTROL_DETAILS.md), and [recovery files and permissions](RECOVERY_FILES_AND_PERMISSIONS.md). No new hardware investigation was performed to prepare it.

**Evidence classes:** *Observed* means a prior read-only snapshot on 1 November 2026; *source-derived* describes the code inspected at that time; *historically reported* is not a new test; *unknown* indicates missing proof. These snapshots do not establish the present system state.

## 1. Sensor-selection documentation discrepancy

The prior branch-specific source analysis documented in the temperature inventory inspected `fan/thermal_curve.c:136–151, 154–208, 754–803`: CPU names `coretemp`, `k8temp`, `k10temp`, `zenpower`; the reported CPU value comes from the first valid glob-sorted input of the first usable matching device, while the curve prefers the maximum `cpu_peak_celsius`. The general [software fan-curve document](FAN_CURVE.md) instead lists `coretemp`, `k10temp`, `zenpower`, `cpu_thermal`, `acpitz` as CPU sources and describes highest-temperature sampling. These descriptions are **not equivalent**. They may reflect different revisions or documentation drift; their exact cause is **unknown**. For the previously inspected branch and evidence, the branch-specific interpretation is recorded in [fan-control details](FAN_CONTROL_DETAILS.md); re-check the selected source revision before a future recovery rather than assuming either list applies universally.

The general document also says the guarded ATA fallback never wakes a parked disk. The inspected branch source was reported to issue a power-mode check and skip SMART READ DATA unless the drive is reported running. Actual behavior through every ATA/SAT bridge and its impact on standby were **not tested**; a universal no-wake guarantee is not established. No ATA/SMART command was issued by the prior sensor inventory itself. The already running daemon may independently issue them.

## 3. Kernel module evidence beyond package ownership

**Observed, 1 November 2026:** `modinfo it87` for the installed Debian kernel module reported `vermagic=6.12.113+deb13-amd64 SMP preempt mod_unload modversions`, `license=GPL`, `intree=Y`, dependency `hwmon-vid`, and signer `Build time autogenerated kernel key` with signature hash algorithm `sha256`. The optional parameters were `force_id` (ushort array), `ignore_resource_conflict`, `update_vbat`, and `fix_pwm_polarity`; the latter was marked dangerous by `modinfo`. None was established as a required setting, and runtime parameters could not be inspected because `it87` was not loaded. A signature field does **not** prove successful verification or Secure Boot trust.

The examined local `/etc/modprobe.d` and `/etc/modules-load.d` files and `/etc/modules` had no `it87`/`force_id` entry; this does not exclude initramfs, other configuration sources or historical settings. DKMS status showed `led-ugreen/0.3` for the kernel, not `it87`. Module path, compressed-file hash, exact model mapping and direct-access safeguards are in [fan-control details](FAN_CONTROL_DETAILS.md).

## 4. Historical artifact comparison and unresolved provenance

**Observed, 1 November 2026:** the three already-existing comparison CLIs in the feature worktree, Debian documentation worktree, and a separate temporary build had identical SHA-256 `949e32d01329c69b25bdb43e370f4da391c2151045c6d2ea98d827fae1fa2bad` and ELF build ID `556afdf244ed119330fff47e231d2f02f917fa54`; none matched the installed CLI. A separate older-worktree candidate had 307720 bytes, SHA-256 `5d29c90152eb99955c54e39a4e467899683fce95712e0978803e7946638567dc`, build ID `743562c54048e45e1ffccbdc4f3400239e8e09ee`, also not a byte match. Other examined archived preview CLIs had different sizes and hashes. Similar symbols and compiler metadata do not establish identical machine code or source origin.

The examined caches used Release, `/usr/bin/cc`, `-O3 -DNDEBUG`, prefix `/usr/local`, libdir `lib`; the older candidate used Ninja and the three comparison builds used Unix Makefiles. The older source tree was at `main` commit `f714831d37d49ca0b95771c22de85488f2f2fc21` with local changes; that versioned thermal-curve source lacked `failure_threshold`, which appeared in later inspected source. These facts do not identify the installed CLI's origin. The caches describe the **remaining builds**, not necessarily the build originally installed. The observed installation history included a relative `build/ugreenctl` source, but not a verified working directory, source hash, execution success or reliable installation time. The exact historical CLI source and installation chain remain **unknown**; the primary recovery decision is a fresh source build, not a claim of bitwise equivalence.

## 5. Preserved historical validation boundaries

**Historically reported:** the earlier stress/cooling observation and speaker tone test are summarized in [fan-control details](FAN_CONTROL_DETAILS.md); those observations did not provide complete raw logs, firmware/driver versions or an automatic alarm test during real failure. The subsequent `thermal-curve` and `fan-failure` fixture tests passed, but no complete fresh-install, independent airflow, sensor-loss injection, kernel-update or supervised rollback validation was established.

State-file `applied_*` values, actual hardware register readback, independently measured tachometer RPM and physical airflow are four distinct evidence levels. A successful command or failsafe request does not prove the latter levels, and a failed first-channel write can prevent a later-channel attempt. Any future verification requires separate authorization, exclusive controller ownership and an independently safe cooling and shutdown plan.
